# ADR-044 — key reduction checked on the played result

Status: Accepted
Date: 2026-10-21

## Context

Artists ask for fewer keys so that they can keep editing a file by its poses. Two sources leave keys that say nothing:

- **Baked or fitted motion.** Procedural layers, key poses fitted frame by frame and video fits key many frames; ADR-038 re-keys bone timelines inside the build within 0.25 degree or px of the compiled motion. That cleanup sees one channel at a time, in local units, and never looks at what the runtime draws.
- **Hand-made files.** The mummy cat Jackpot file (Spine 4.0.64, 30 fps, 81 bones, 95 meshes of which 53 weighted, 6 IK and 5 transform constraints, five animations) has 4,580 keys. 2,031 of them sit on timelines that never change: scale and shear keyed to their defaults on every pose with stepped curves ("key all"). The motion keys themselves are already pose to pose.

A reduction an artist can trust needs a stated error on the drawn result, not on channel values: an angle that is harmless on a fingertip moves a whole body, and many channels inside their own tolerance can add up.

## Decision

`reduceSpineKeys` in `@autospine/reference` reduces the keys of a Spine 4.0 JSON document. The CLI `reduce-keys`, the MCP tool `autospine_reduce_keys` and the character build (`motion.keyReduction`) all call it.

- **Timelines as numbers** (`keys-timeline.ts`): every curve timeline (bone rotate/translate/scale/shear and their x/y forms, slot rgba/rgb/alpha/rgba2/rgb2, IK, transform, path position/spacing/mix, deform) becomes key times, value vectors and per-channel curves. Deform keys are expanded to full offset vectors (offset and omitted zeros; weighted meshes by weight pairs, linked meshes through their parent) and written back trimmed. Rotation values are never wrapped, so multi-turn and ±180° keys keep their path. Attachment, draw order and event keys are only read for their times and are never rewritten.
- **The runtime's curve** (`keys-fit.ts`): spine-core 4.0 flattens a Bezier into ten straight pieces; fitting and every channel error use those pieces, not the exact curve. Fitted segments use per-channel Spine Bezier handles (one shared curve for deform, as the format has), time handles inside the segment and in order (time runs forward, as the editor draws it), value handles bounded by the samples' range.
- **Two modes, each with its own limit** (world vertex px; defaults 0.1 % / 0.03 % of the skeleton's height for `fidelity`, 0.3 % / 0.1 % for `posable`, max / RMS). A limit is never widened to reach a ratio; a failing animation keeps keys or falls back instead.
  - `fidelity`: per timeline, the fewest original keys whose refitted segments stay within the channel tolerance (dynamic programming over the original keys). Neighbouring kept keys keep their original segment.
  - `posable`: bones whose turning frames agree (Jaccard ≥ 0.5 with their nearest animated ancestor) form a group that shares pose frames; the main group nearest the root gets named pose nodes from its height and the ground contacts (anticipation/compression, launch, takeoff, apex, landing, cushion, recovery; for loops low, high, support, passing, airborne). A group that repeats its anchor's motion later (circular cross-correlation of rotation speed ≥ 0.5 at a lag of 0.5–10 frames) is a follow part and keeps its own turning frames. New keys go on whole frames; a turn within a frame of an original key takes that key's own time (sub-frame or not). Segments past tolerance get keys at their worst whole frame.
  - Deform in both modes: important shapes first (turns of the shape's distance and main axis), then a key where an interval is off, only in that part and interval.
- **Channel tolerances only pre-filter**: half the world limit (`localShare`) divided by what one unit moves on screen — rotation and shear by the bone's reach (the farthest vertex it moves, at least 5 % of the skeleton), translation by the parent's world scale, scale by the reach, mixes by the constrained bones' reach. Colour keys use 1/255.
- **Protected**: first and last keys; both ends of a stepped jump and of a zero-length segment (kept verbatim); a key where IK bend, compress or stretch switches; keys on event times; locked keys and timelines; keys on visible peaks and rebounds (prominence of the full limit). A constant timeline keeps one key — it still holds its value when animations are mixed — and the animation keeps its length (an end key is put back if no kept key reaches it). No timeline is removed.
- **Acceptance is the played result** (`keys-world.ts`): the original and the candidate play on the official runtime (hierarchy, weights, IK, transform and path constraints, deform). Samples: four a frame, every key time and 0.1 ms either side, 0.1 ms either side of every attachment, draw order and event key, the last instant before the loop wraps; then quarter points of every interval with an end over half the limit, up to three rounds. Max is the largest vertex distance; RMS the square root of the mean squared distance over every compared vertex of every sample. Slots shown in either version are compared; a different attachment, visibility or draw order is a state mismatch and fails the animation. Passing means the sampled times are within the limits, not a continuous-time guarantee.
- **Local correction and fallback**: always against the immutable original. At the worst sample, the timeline behind the worst part with the largest error (times its screen lever) gets a key there (fidelity: the nearest original key; posable: the whole frame), and only the changed interval is resampled. Past the insertion budget, or when nothing is left to add, the timelines behind that part go back to their original keys; if it is still off, the whole animation does. Every insertion and fallback is reported.
- **No compounding**: the result is deterministic. With `baseline` (the untouched original of an earlier run), an animation that still plays within the limit of the baseline's is reduced again from the baseline — the same output — so running again never adds error; one edited past the limit is reduced as it is now.
- **Report** per animation and timeline: keys before and after (and how many came from constant timelines), mode, limits, sampling, max and RMS, worst time, frame and part, pose nodes and the error there, motion groups, follow lag and turning-time shift, ground contact slide, loop seam pose and speed jump, state mismatches, insertions, fallbacks and why a timeline was skipped, locked, constant or restored.
- **Files** (`reduce-keys`): a `.spine` is exported with the editor CLI (default 4.0.64); the source's SHA-256 is compared before and after. Each mode writes JSON, a `.spine` imported with the editor, that project's export (`roundtrip/`), and `key-report.json`; the editor export is played against the reduced JSON and against the source (the formal output). The untouched source's own editor round trip is measured for scale. A preview video (original | fidelity | posable: wireframe, bones, motion) and an HTML report with a key-time sheet per animation complete the output. The MCP tool runs the same step on workspace JSON without the editor.
- **Build**: a plan with `motion.keyReduction` compiles with every key (the ADR-038 cleanup is skipped) and reduces the compiled file against that exact motion; `key-reduction.json` goes beside the build.

## Consequences

- An artist file keyed with "key all" loses its redundant keys with a stated, verified error; a baked or fitted animation loses most of its keys.
- `posable` trades some count for keys on poses; on files already keyed pose to pose it mostly keeps the artist's keys.
- The checks use what the runtime draws in skeleton units; a display scale is not known to the file and is not applied. Interpenetration is bounded by the vertex error, not detected separately.
- Rollback: remove `keys-*.ts`, the CLI command, the MCP tool and `motion.keyReduction`; ADR-038 stays as it was.
